# Work log, 21 November 2026

What was built and learned in one long bench session, in the order it happened. The reference detail lives in [DESIGN.md](DESIGN.md); this page is the story and the "how do I use it".

Setup: gateway (ESP32-S31 + E52, on the home LAN at 192.168.1.22), node 4498 (site `TEST-01-02-034-05W5`, R4AVA07 analog board), node 22B1 (site `TEST-02-FRONT`, R44VL04 board). All on branch `perf/usb-e52-latency`.

## 1. Second node joined the mesh

- Node 22B1 was built and flashed. It kept dropping out; the causes were an intermittent 5 V wire and a cold ground joint, not radio.
- Its RTU (R44VL04) answers at unit 1, 9600 8N1. Digital inputs are discrete inputs 0–3 (terminal N = address N−1, grounded reads 1). Holding registers 0–3 are the analog channels; scaling still unknown.
- Poll list sent over the mesh: `di1`–`di4`, `ai1`–`ai4`, every 30 s, published to `lmesh/9D44/TEST-02-FRONT/data`.
- Modbus TCP unit 2 → node 22B1, RTU address 1. The first attempt returned exception 0x0B because the Unit Map's third field was left at 0 ("same as TCP unit").

**Useful to remember:** `lmesh/9D44` is the gateway; every node appears under it by site ID.

## 2. Node display and RSSI

- **OLED on the node** (D9/D10, 3V3, GND). Shows site, mesh address, RSSI and next hop to the gateway, RTU counters, last publish, poll values. Your 1.3" modules are SH1106, which is now the default. One panel had dead pixel rows; the second was clean.
- **RSSI everywhere:** a Link column on the gateway's Nodes page ("direct −45 dBm" or "via 4498 −19 dBm"), `rssi` and `hop` in each node's MQTT status, and a line on the node's own page.

## 3. Changing the air rate of the whole mesh

Gateway page → Radio → **Change mesh rate**.

- Every node is told the new rate and a countdown, so all switch together. Then the gateway pings them on the new rate.
- A node keeps the new rate only after it hears the gateway on it. Otherwise it goes back by itself after 3 minutes. If no node answers, the gateway goes back too.
- Tested: 1 → 2 → 0 → 1 with two nodes, and the fallback with a node deliberately sent to the wrong rate.

**The one trap:** a node that is off or unplugged during a change stays on the old rate. It happened to 22B1 when it was moved mid-change. Switch the mesh back (tick "leave behind nodes that do not answer") to recover it.

## 4. Speed tests and making 7 kbps work

Modbus reads of 4 registers through the gateway, both nodes:

| Rate | Median | Reliability |
|---|---|---|
| 0, 62.5 kbps | ~255 ms | fine, but only 60 ms faster than rate 1 and 6 dB less range |
| 1, 21.9 kbps | ~320 ms | 100 of 100, no retries |
| 2, 7 kbps, at first | ~700 ms | 23 % of reads retried, some took 5 s, 37 % of pings lost |
| 2, 7 kbps, now | ~1 s | 50 of 50, no retries, slowest 2.2 s |

What fixed rate 2:
1. **Wait after receiving before sending** (300 ms at rate 2). The two radios are still exchanging their own acknowledgement; a reply sent too soon is lost.
2. **A retry timer sized for rate 2** (about 2.4 s).
3. **Not resending when the module says "no ack".** That experiment made it worse: the E52 already retries by itself, and "no ack" mostly means the acknowledgement was missed, not the frame.

Sensitivity, for range planning (datasheet figures from memory, ±2 dB): about −111 / −117 / −123 dBm at rate 0 / 1 / 2. Rate 2 should give roughly double the free-space distance of rate 1.

## 5. Firmware updates without a cable

All three boards now have two firmware slots. That needed one last USB flash each; settings survived.

| Update | Where | Time |
|---|---|---|
| Gateway | gateway page → Firmware card → `build\lmesh_gw.bin` | 4 s |
| Node, standing nearby | join `LMESH-NODE-xxxx`, node page → Firmware card → `node\build\lmesh_node.bin` | not tried yet |
| Node, from anywhere | gateway page → "Node firmware over the mesh": store the file once, pick a node, Send | 46.5 min at rate 1, one hop |

Safety, the same everywhere: the file is checked first (a gateway file is refused by a node, a damaged file is refused), the new firmware runs on trial, and a board that cannot prove it is still reachable goes back to its old firmware after 10 minutes.

The first mesh update delivered every byte and was then refused: the final checksum did not match. One packet in about 6,000 had arrived damaged. Each packet now carries its own checksum; the second run caught exactly one damaged packet, resent it, and the node installed, restarted and confirmed.

A two-hop update (to 22B1, relayed through 4498) was started at the end of the session; see the note at the bottom.

## 6. Things I got wrong along the way

Worth knowing, so the reasoning in the code makes sense:

- Predicted rate 2 would be three times slower than rate 1; a clean read is about twice as slow.
- Built an automatic resend on "no ack"; it made things worse and is switched off.
- Guessed the first OLED's missing rows might be my start-up settings; it was the panel.
- Estimated mesh updates at 30–60 minutes; measured 46.5.
